# ANUSANDHAN Architecture

This is a conceptual architecture. No code implements it yet.
It constrains future work so growth stays modular and reproducible.

## Design goals

- CPU-first. Early experiments must run on a standard CPU machine.
- Reproducibility. Every result traces to code, data, seed, and environment.
- Small modules. Each component has one responsibility and a stable interface.
- Honest boundaries. Research prototypes stay separate from stable APIs.

## Conceptual layers

```text
documentation (vision, principles, roadmaps)
        |
research proposals (research/)
        |
experiments (future: small, seeded, CPU-based)
        |
evaluation (future: metrics, baselines, reports)
        |
stable APIs (future: versioned interfaces only)
```

Only the top two layers exist today. Lower layers are defined before they are built.

## Data layer (future)

- Every dataset needs a dataset card: source, version, license, and intended use.
- Raw data stays immutable. Processed data is generated by versioned scripts.
- No dataset is added without a compatible license.
- Biomedical, biometric, and personal data need extra review.

## Experiment layer (future)

- One experiment equals one config plus one seed plus one environment lock.
- Configs are declarative and checked into version control.
- Randomness is seeded and logged.
- CPU budgets are stated in advance (time and memory).

## Evaluation layer (future)

- Baselines come first. No method is reported without comparison.
- Metrics are defined before runs, not selected after.
- Failures and negative results are recorded.
- Demonstrated results stay separate from research goals in every report.

## Interface boundaries

- Internal research code never becomes a public API by accident.
- A stable API requires documentation, versioning, tests, and a changelog entry.
- Integration with KryomCode and KryomAI, if ever needed, uses such stable APIs only.
- No shared internals, models, or private dependencies are assumed.

## Repository conventions

- `docs/` holds durable decisions and plans.
- `research/` holds proposals and experiment records.
- Source code appears only when a proposal is approved.
- Empty placeholder modules and speculative domain folders are not used.

## Non-goals at this stage

- No model training infrastructure.
- No GPU-dependent pipelines.
- No production serving.
- No clinical, robotic-hardware, or laboratory control systems.
