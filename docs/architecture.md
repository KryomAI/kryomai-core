# KryomAI Core Architecture

Conceptual architecture for KryomAI Core. No code implements it yet.
It constrains future work so growth stays modular and reproducible.

See [glossary.md](glossary.md) for terms and [decisions.md](decisions.md)
for binding decisions.

## Design goals

- CPU-first. Early work must run on a standard CPU machine.
- Reproducibility. Every result traces to code, data, seed, and environment.
- Small modules. Each component has one responsibility and a stable interface.
- Honest boundaries. Research prototypes stay separate from stable APIs.
- Evidence-gated growth. Stages advance on exit criteria, not dates.

## Conceptual layers

```text
documentation (vision, principles, roadmaps, strategies)
        |
research workflows (research/: proposals, records, dataset cards)
        |
experiments (future: small, seeded, CPU-based)
        |
evaluation (future: metrics, baselines, reports)
        |
training (future: gated by stage, see training-strategy.md)
        |
serving (future: gated by stage, see inference-and-serving.md)
        |
stable APIs and SDKs (future: versioned interfaces only)
```

Only the top two layers exist today. Each lower layer is defined in
its strategy document before anything implements it.

## Core, research, and product boundaries

- KryomAI Core owns research, models, evaluation, and the stable
  API/SDK surface. Nothing else.
- Research workflows live in `research/` and follow
  [research-principles.md](research-principles.md). They never become
  public APIs by accident.
- Products (KryomLabs Platform, KryomCode, and the others named in
  [product-integration.md](product-integration.md)) own their
  engineering and repositories. They consume Core only through
  stable, versioned APIs.
- No shared internals, models, or private dependencies cross these
  boundaries in either direction.

## Data layer (future)

- Every dataset needs a dataset card: source, version, access date,
  license, permitted uses, preprocessing, limitations, and biases.
- Raw data stays immutable. Processed data is generated by versioned scripts.
- For R0–R2, only public-domain and clearly open-licensed datasets.
- No dataset is added without a compatible license.
- Biomedical, biometric, and personal data need extra review.

## Experiment layer (future)

- One experiment equals one config plus one seed plus one environment lock.
- Configs are declarative and checked into version control.
- Randomness is seeded and logged.
- CPU budgets are stated in advance (time and memory).

## Evaluation layer (future)

- Baselines come first. No method is reported without comparison.
- Metrics are defined before runs, not selected after.
- Failures and negative results are recorded.
- Demonstrated results stay separate from research goals in every report.

## Training layer (future)

- No training runs exist. Training begins with tiny CPU studies under
  R2 budgets and advances only through stage gates.
- Strategy, not code, comes first: see
  [training-strategy.md](training-strategy.md).

## Serving and interface layer (future)

- Nothing is served today. Serving and APIs arrive only through the
  stable-interface exit criteria.
- A stable API requires documentation, versioning, tests, and a
  changelog entry.
- SDKs are Python-first when built.

## Repository conventions

- `docs/` holds durable decisions, plans, and strategies.
- `research/` holds proposals and experiment records.
- Source code appears only when a proposal is approved.
- Empty placeholder modules and speculative domain folders are not used.
- Full layout rules live in
  [repository-structure.md](repository-structure.md).

## Non-goals at this stage

- No model training infrastructure before its stage gate.
- No GPU-dependent pipelines in R0–R2.
- No production serving.
- No clinical, robotic-hardware, or laboratory control systems.
- No framework or vendor commitments (D8).
